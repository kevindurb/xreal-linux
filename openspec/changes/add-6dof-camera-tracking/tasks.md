# Tasks

## 0. Find out how the Eye is started (blocks everything below; discovered during implementation)

The Eye's camera stream (port 52997) has been seen only while the glasses' own menu is in anchor mode; in Follow mode with the Stabilizer off, which this change requires, it is idle (`docs/findings.md`, "Capture recorder check"). The design assumed it would stream. Static analysis of the vendor SDK (`docs/nebula-findings.md`, `docs/xreal-link-messages.md`) shows the glasses speak a request/response protocol in which the camera has start/stop requests. The requests go to **TCP port 52999** in a transaction-id frame (`docs/xreal-link-messages.md`, section 13); what is not known is whether the 1S honours the camera requests and whether Follow mode allows it.

- [x] 0.1 Analyse the vendor SDK offline and document the message framing and ids. Verify: `docs/xreal-link-messages.md` lists the ids, the framing is checked against every recorded capture (`tools/test_xreal_link.py`).
- [x] 0.2 Observation run: record all ports and the glasses' HID endpoints while the glasses' own menu switches anchor mode on and off, following `docs/anchor-capture-plan.md`. Verify: `tools/xreal_link.py` summary of the capture, with the camera start visible (or its absence recorded), and the findings written to `docs/findings.md`. Done 2026-10-08 (`anchor-03`): the camera streamed only in anchor mode, at 15 fps; start/stop announced by message 10002 on port 52999; no traffic on HID or on ports 52990-52995; see `docs/findings.md`.
- [x] 0.3 Find the request port and framing. Done 2026-10-08: the control port is 52999 and requests carry a transaction id (framing from the public `one-xr` library, checked against our captures); the earlier attempts failed because they went to ports 52990-52995 without one. Evidence in `docs/xreal-link-messages.md` section 13.
- [x] 0.4 Send the first read-only request with the wearer's approval. Done 2026-10-08 with `tools/xreal_probe.py --txid --port 52999 --id 0x271f` (`GetConfig`): one 220 KB JSON reply, and the glasses' streams and display mode were unaffected afterwards.
- [ ] 0.5 Decide the start mechanism (progress 2026-10-08: **a host request does start the camera in Follow mode** with the Stabilizer off, but a bare Create and Start gives only four frames, see `docs/findings.md`; what keeps it streaming is open): (a) a host request that starts the camera in Follow mode with the Stabilizer off, (b) the camera needs anchor mode (then the change is re-scoped or stopped), or (c) not possible. Verify: the decision and its evidence are written to `docs/findings.md`, and `design.md` is updated; for (a), the exact request, port and any handshake are documented.
- [ ] 0.6 (Create 10047 and Start 10053 were sent and answered on 2026-10-08, with four frames at 15 fps and no reply to Stop 10054; next candidates: the `InitSet*` requests 10048-10052, an IMU/vsync session on the same connection, a repeated Start, the SDK's own `1a 00` body.) If (a) looks possible: from the layouts in `docs/xreal-link-messages.md` section 8, build the `NRGrayscaleCameraCreate` (10047) and `NRGrayscaleCameraStart` (10053, inferred) requests and the matching Stop (10054), with any read-only query of the current state first; show the exact bytes to the wearer and send only with their explicit approval, one request at a time, extending the probe tool's allowlist for these ids only. Verify: camera frames (id 10056) appear on port 52997 in Follow mode with the Stabilizer off, about 60 fps (or the rate the glasses give), the start event (10002) shows on 52999, Stop ends them, and the glasses' display and tracking are unaffected (checked by the wearer with SteamVR Home).

## 1. Decode the Eye stream and put it on the IMU clock (research first; everything else depends on it)

- [ ] 1.1 Record 60 s of ports 52997, 52996 and 52998 together (use `tools/capture_eye.py`; the camera needs the start mechanism from group 0) while the glasses sit still, are shaken, and are rotated slowly. Store under a capture directory outside the repo with a documented format. Verify: the capture replays frame by frame and a size/count summary matches the live rates (about 60 fps, 120 records/s, IMU rate).
- [ ] 1.2 Settle the image geometry and pixel packing: the config says the camera is 504 x 378 and a recorded frame suggests the stream carries every second row (189 of 378) with 512 stored columns; show a printed grid at known angles and fit the unpacking so lines are straight and the aspect is right, and decide whether the missing rows are skipped or binned; record the result (including why the left half is interleaved) in `docs/findings.md`. Verify: a decoded frame of the grid has straight lines and the correct aspect, saved as a PNG (kept out of the repo).
- [ ] 1.3 Identify the frame timestamp field (found 2026-10-08: a little-endian u64 of nanoseconds at packet offset 23, 66.8 ms apart at 15 fps; still to check against the IMU clock and the 52996 records) and measure the camera-to-IMU lag with the shake capture (gyro magnitude against optical-flow magnitude). Verify: the measured lag and its spread are written to `docs/findings.md`, and the within-5-ms requirement is met or the shortfall is stated.
- [ ] 1.4 Write the C++ reader/decoder for the camera stream (frame sync, resync after a short frame, reconnect, absent-camera handling) with unit tests on recorded frames. Verify: unit tests pass in the fedora:44 container, and a live run on the Deck prints about 60 decoded frames/s.
- [ ] 1.5 Record/replay tool that feeds a capture through the same reader. Verify: replaying a capture yields byte-identical decoded frames to the live run that produced it.

## 2. Calibration (starts from the glasses' factory values; the fitting tasks are the fallback)

- [ ] 2.1 Factory calibration reader and store: a read-only `GetConfig` client with a timeout, a parser for the SLAM-camera intrinsics, `imu_p_cam` and `imu_q_cam` (JPL quaternion order) and the stored time offset, and a per-serial cache outside the repo that refuses a mismatched device. Verify: unit tests on a recorded response with the serial replaced by a dummy (a parse test, a cache write/read test, a mismatch refusal test); on the Deck the reader prints the camera size, focal length and the config's `last_modified_time` for the connected glasses.
- [ ] 2.2 Check the factory intrinsics and extrinsics: capture a checkerboard from several angles (and the shake capture from 1.3) and score the reprojection error with the vertical values halved and unscaled; document the thresholds. Verify: the tool prints the error for each case; the chosen scaling and the numbers are written to `docs/findings.md`.
- [ ] 2.3 Time offset: take the offset measured in 1.3 and store it per serial beside the cache. Verify: a run without a stored offset reports that tracking cannot start, and with one it uses it (unit test).
- [ ] 2.4 Only if 2.2 fails its thresholds: intrinsics tool (checkerboard views, pinhole and equidistant fits with OpenCV, pick by reprojection error) and a camera-IMU capture session converted for Kalibr (extrinsics), writing a calibration that overrides the factory values and refuses poor results. Verify: reports error per model, and Kalibr prints a solution with a stated residual. Skip, noting why, if 2.2 passes.
- [ ] 2.5 Offline scoring of a capture against a calibration. Verify: scoring the calibration capture reproduces the reprojection error the tool reported.
- [ ] 2.6 Document the procedure in a README (printed target, motions, thresholds, what the factory check does). Verify: someone following only the README gets a stored time offset and a passed check (user check).
